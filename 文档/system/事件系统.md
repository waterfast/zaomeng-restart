# Godot 事件系统与装备交互

事件资源在 `GameData/Events`，代码在 `Scripts/Events`。对应 Unity 的 ScriptableObject 事件通道：发送者和接收者持有同一个 `.tres`，不需要彼此查找节点。`GameplayEvents.tres` 汇总当前关卡使用的通道，已注入 TestArena 和前三关。

## 请求与通知

| 资源 | 类型 | 约束 |
| --- | --- | --- |
| `EquipmentRequested.tres` | 同步请求 | 仅一个处理者，返回 `EquipmentResult`；未绑定、重复绑定、嵌套请求都有明确处理。 |
| `ItemActionRequested.tres` | 同步请求与只读选项查询 | 按类别/物品查找操作，执行前复检物品身份与可用条件；详见 [ItemActions.md](物品操作系统.md)。 |
| `ItemActionCompleted.tres` | 无参数通知 | 物品操作成功提交并尝试保存后刷新背包、属性和余额；失败不广播。 |
| `EquipmentChanged.tres` | 类型化通知 | 多个观察者；携带角色 ID、装备槽、新旧装备实例快照。 |
| `GemRequested.tres` | 同步请求 | 按实例 ID 镶嵌/拆卸，检查孔位与宝石来源；与穿戴请求共享操作保护。 |
| `EquipmentModified.tres` | 类型化通知 | 实例数据修改完成后的通知，携带修改前后不可变快照。 |
| `InventoryChanged.tres` | 无参数通知 | 状态提交后读取最新背包；不会广播交换中间步骤。 |
| `SaveFailed.tres` | 字符串通知 | 物品操作已完成、写盘失败的独立提示。 |

通知用于已发生的事实，不能依赖监听顺序执行扣物品或修改槽位。每个监听者独立执行，监听异常记录后继续其他订阅。订阅期间增加的监听者下次才生效，已释放的监听者不会继续接收本次通知。所有通道按 Godot 主线程同步执行，不提供跨线程调度。

资源只保存配置说明和资源引用；处理者、订阅、最近发送者与发送次数均不序列化，也不进入玩家存档。运行时检查器显示只读调试字段。不要复制一份事件资源给发送者，否则会连接到不同通道；离开场景时释放本场景的连接，不要清空其他模块的订阅。

## 使用方式

```csharp
// 请求：界面传真实背包索引和选中时的实例 ID，同名装备也不会混淆。
EquipmentResult result = events.EquipmentRequested.Send(
    new EquipmentRequest(EquipmentAction.Equip, entry.SlotIndex, entry.Equipment!.InstanceId), this);
if (!result.Success) ShowFeedback(result.Message);

// 通知：保存连接，在所属对象退出或 Dispose 时释放。
IDisposable connection = events.EquipmentChanged.Subscribe(change => RefreshEquipment());
connection.Dispose();
```

`IntEventChannel`、`StringEventChannel`、`VoidEventChannel` 为通用通知资源。`IntEventListener`、`StringEventListener`、`VoidEventListener` 为可放入场景的监听节点：检查器指定资源，再连接节点的 `Received` Godot 信号。进入场景树时订阅，退出时取消；重新进入会重新连接。节点暂停不自动退订，适合暂停游戏时仍工作的背包。需要运行时更换通道时，先移出场景树，再设置资源并重新加入。

新增业务消息时，先定义有明确字段的 C# 数据，再按 `EquipmentChangedChannel` 封装类型化资源。Godot 可注册的具体资源类使用 `[GlobalClass]`；泛型分发逻辑通过普通 C# `NotificationChannel<T>`、`RequestChannel<TRequest,TResult>` 复用，不用 `object` 强制转换业务数据。

## 基本服务

- `InventoryService`：背包格子与数量规则。内部交换在副本上校验容量，最后一起提交背包与穿戴槽，再通知观察者。
- `EquipmentService`：等级、角色、类型、格子与预期物品检查；穿戴/卸下统一入口。正常失败返回结果，背包与穿戴状态保持原样。
- `GameplayEquipmentBinding`：关卡装配层，注册唯一请求处理者；应用 Player 属性、转发通知、调用保存，离场释放连接。Player 不再承担保存职责。
- `GemSocketService`：背包或当前角色上的装备均可镶嵌/拆卸；消耗、归还宝石与实例修改统一提交。
- `LegacyBackpackView`：单击物品打开自定义操作框，点击菜单请求装备、出售、使用或打开宝箱；穿戴槽显示“卸下”菜单与完整属性说明。右键装备打开 `GemSocketView`，显示失败原因并订阅实例变化。

满背包换装会考虑新装备移出后腾出的空间；直接卸下则必须有容纳旧装备的空间。空槽卸下不额外保存，同种装备的不同实例允许正常换装。内存提交与磁盘保存不是同一个事务：保存失败后装备仍然生效，通过 `SaveFailed` 提示，不自动回滚、不自动重试。

装备已使用独立实例，实例 ID 与宝石孔随背包、穿戴和存档转移；强化和词条可在实例数据上增加实际需要的字段。玩家数据不能放进共享物品资源或事件资源。数据模型详见 [EquipmentInstances.md](装备实例系统.md)。

原 `--equipment-architecture-test` 已改用真实背包交换和新的装配层，继续验证属性计算与旧界面表现。运行 TestArena 或关卡的测试时应使用独立用户目录。
